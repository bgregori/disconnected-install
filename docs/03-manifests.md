# Manifests before ignition

There is a window in the install process — after manifests are generated,
before ignition configs are — in which you can add resources that will be
baked into the node images. Three things in a hardened build have to
happen in that window, and all three are expensive or impossible to add
afterwards.

This is the highest-stakes chapter in the repository and the one with the
fewest commands, because the window is easy to describe and the contents
are not.

---

## The window

There is no single window. There are **two staging points, at different
stages, in different directories, with different file formats** — and
the thing most likely to end in an unencrypted cluster is putting
something in the first one that belongs in the second.

```
install-config.yaml + agent-config.yaml
        │
        │   ◄── STAGING POINT 1: <install-dir>/openshift/
        │         A directory YOU create and fill before anything
        │         below runs. MachineConfigs, Butane output,
        │         cluster-scoped config. NOT disk encryption.
        │
        ├── agent create cluster-manifests
        │       consumes and DELETES install-config.yaml and
        │       agent-config.yaml; their settings are imported
        │       into the ZTP manifests it emits
        │
        │   ◄── STAGING POINT 2: <install-dir>/cluster-manifests/
        │         agent-cluster-install.yaml. Generated by the step
        │         above, then hand-edited. THIS is where disk
        │         encryption goes.
        │
        └── agent create image ────────────► ISO
                                             nothing added after this
                                             point reaches a node at
                                             first boot
```

Earlier drafts of this chapter described a pause between `create
manifests` and `create ignition-configs`. **The agent workflow has no
such pair, and that framing is withdrawn.** It is the classic
installer's model and it does not transfer. The diagram above replaces
it.

What changed, and why it matters more than a correction usually does:

| Was drafted | Actually |
|---|---|
| One window, after manifest generation | Two staging points, one before and one after `create cluster-manifests` |
| Disk encryption is a `MachineConfig` in `openshift/` | Disk encryption is a `diskEncryption` block in `cluster-manifests/agent-cluster-install.yaml` |
| Inspect on a scratch copy, because generation consumes the inputs | Generation **must** run on the real directory, because its output is what you then edit |

The third row is the one that bites. The previous draft told you to run
`agent create cluster-manifests` against a throwaway copy so as not to
lose `install-config.yaml`. Do that and you throw away the very file
disk encryption has to be written into. Take backups instead — chapter 4
does, immediately before generating the ISO, and that is now too late to
be the only copy.

### Staging point 1 — `openshift/`

Built by hand, before any `openshift-install-fips` subcommand runs:

```sh
# ===== RUN ON: THE INSTALL HOST =====
: "${OCP_INSTALL_ROOT:?set it first -- see 01-intake.md}"
mkdir -p ${OCP_INSTALL_ROOT}/manifests-src
mkdir -p ${OCP_INSTALL_ROOT}/cluster/openshift

cp ${OCP_INSTALL_ROOT}/manifests-src/*.yaml \
   ${OCP_INSTALL_ROOT}/cluster/openshift/

ls -l ${OCP_INSTALL_ROOT}/cluster/
ls -l ${OCP_INSTALL_ROOT}/cluster/openshift/
```

```
${OCP_INSTALL_ROOT}/cluster/
  install-config.yaml       consumed and deleted by create cluster-manifests
  agent-config.yaml         consumed and deleted by create cluster-manifests
  openshift/                ◄── STAGING POINT 1, filled before anything runs
    98-master-chrony.yaml
    98-worker-chrony.yaml
```

Two chrony files, not four. The storage pair the previous draft put here
has moved to staging point 2 and is no longer a file.

### Staging point 2 — `cluster-manifests/`

Back up the inputs, then generate. The backup is not optional here: the
command deletes both files, and one of them is the only record of what
you authored in chapter 2.

```sh
# ===== RUN ON: THE INSTALL HOST =====
: "${OCP_INSTALL_ROOT:?set it first -- see 01-intake.md}"
cp ${OCP_INSTALL_ROOT}/cluster/install-config.yaml \
   ${OCP_INSTALL_ROOT}/install-config.yaml.bak
cp ${OCP_INSTALL_ROOT}/cluster/agent-config.yaml \
   ${OCP_INSTALL_ROOT}/agent-config.yaml.bak
chmod 600 ${OCP_INSTALL_ROOT}/*.bak

openshift-install-fips agent create cluster-manifests \
  --dir ${OCP_INSTALL_ROOT}/cluster --log-level=info

ls -l ${OCP_INSTALL_ROOT}/cluster/cluster-manifests/
ls -l ${OCP_INSTALL_ROOT}/cluster/openshift/
```

That second `ls` is the one worth doing, and it is now the open
question rather than a formality. If `openshift/` is empty after the
run, your chrony MachineConfigs were consumed rather than carried —
record that and fix it here before anyone generates an ISO.

Two rules that hold regardless:

- **The install directory gets wiped by a re-run.** `openshift-install`
  deletes and regenerates its contents. Keep your MachineConfigs in a
  source directory outside it and copy them in, every time. Editing them
  in place and then re-running is how a node boots unencrypted.
- **The ISO is the boundary.** After ignition, the only route to node
  configuration is the Machine Config Operator, which means a rolling
  reboot — and for disk encryption, not even that.

## Disk encryption

The requirement: the root filesystem of every node is LUKS2-encrypted,
unlocked without a human typing a passphrase at boot, and unlockable
**only** under the conditions the accreditation specifies.

The failure mode it prevents is the obvious one and is not about
attackers in the building: it is a disk leaving the enclave — RMA, decom,
theft of a whole chassis — carrying etcd, which carries every secret in
the cluster. Encryption at rest inside the cluster
([chapter 8](08-encryption-at-rest.md)) does not help if the disk itself
is readable.

A cluster installed without it **has to be reprovisioned to get it**. For
an accredited build that usually means reinstalling after the finding,
which is why prep raises it at handoff rather than leaving it here.

Two modes, and they answer different questions:

| Mode | Unlocks when | Enclave precondition |
|---|---|---|
| **TPM v2** | the disk is still in its original machine | a TPM 2.0 device, enabled in firmware — and on virtual nodes, a vTPM attached to the guest |
| **Tang / NBDE** | the node can reach the Tang servers | one or more Tang servers reachable **on the node network**, and their thumbprints |

**Pick one. On this installer they do not combine.** The classic path
can bind both with a `threshold`; the agent-based installer's
`diskEncryption.mode` takes a single value, and the section below says
what that costs.

The two fail in opposite directions, and the choice is a site decision
rather than a technical one: TPM alone means a disk moved to another
chassis is useless, but a node whose motherboard is replaced will not
boot. Tang alone means a node that loses the network will not boot, but
a stolen disk is useless anywhere off that network.

> **FIPS is expected to change the cipher.** On a `fips: true` cluster
> the LUKS2 volume should use `aes-cbc-essiv:sha256` rather than the
> modern default, and that is worth writing into the evidence pack
> before an assessor asks why. Whether this installer actually selects
> it is unverified — see *What the cipher will be* below.

> 🚧 **DRAFT -- NOT VALIDATED.** Written from documentation and installer

>

### It is a field, not a MachineConfig

The agent-based installer has a first-class `diskEncryption` block, and
that is the documented route. It goes in `agent-cluster-install.yaml`,
inside `cluster-manifests/`, which means it cannot be written until
`agent create cluster-manifests` has run — staging point 2 above.

An earlier draft of this chapter hand-wrote a Butane config into
`openshift/`. That is the classic installer's route. It is withdrawn as
the primary path here, for two reasons: it is not what Red Hat documents
for this installer, and whether a `MachineConfig` in `openshift/` can
encrypt a root filesystem that the assisted installer is already
provisioning has not been established by anyone here.

It does not get you out of needing `butane` — chrony below still wants
it — but it does mean the binary is no longer on the critical path for
the one decision that cannot be fixed afterwards.

```yaml
# ===== EDIT IN: ${OCP_INSTALL_ROOT}/cluster/cluster-manifests/agent-cluster-install.yaml =====
spec:
  diskEncryption:
    enableOn: all
    mode: tpmv2
```

Three fields, and each one has a trap in it.

**`enableOn` defaults to `none`.** Omit the whole block and you get a
cluster with no disk encryption, generated without complaint, booting
normally. There is no warning because an absent block is a valid
configuration — it is how you ask for no encryption. This is the failure
this chapter exists to prevent, and it is one missing key away at all
times.

`all` is the value to want. The alternatives are `masters` and
`workers`, and choosing `masters` because "etcd is on the control plane"
is the reasoning that leaves worker disks readable — a worker holds
mounted secrets, container images and whatever the workload wrote.

> The installer accepts exactly `none`, `all`, `masters`, `workers`.
> The underlying `AgentClusterInstall` CRD enumerates more — `arbiters`,
> and comma-joined combinations such as `"masters,workers"` — but the
> installer validates against the shorter list and will reject them. If
> you need one, you have left the documented path.

**`mode` is one value, not a set.** Valid: `tpmv2` or `tang`. There is
no threshold, and **no way to express "TPM *and* Tang"** — the
combination that answers "decrypts only in this rack, *and* on this
network". If that is genuinely the accreditation requirement, the
agent-based installer's native field cannot express it, and you are
choosing between relaxing the requirement and leaving this install
method. Find that out now rather than at the assessment.

**Tang needs thumbprints, and the published example omits them.**

```yaml
# ===== EDIT IN: ${OCP_INSTALL_ROOT}/cluster/cluster-manifests/agent-cluster-install.yaml =====
spec:
  diskEncryption:
    enableOn: all
    mode: tang
    tangServers: '[{"url":"http://tang1.enclave.local:7500","thumbprint":"<thumbprint-from-tang1>"},{"url":"http://tang2.enclave.local:7500","thumbprint":"<thumbprint-from-tang2>"}]'
```

`tangServers` is **a JSON string, not YAML** — a quoted scalar
containing a JSON array of `{"url", "thumbprint"}` objects. It is parsed
with `json.Unmarshal`, and a thumbprint is required: the validator
rejects an entry without one. Red Hat's own documentation renders this
field as `tangServers: "server1": "http://tang-server-1.example.com:7500"`,
which is neither the right shape nor carries a thumbprint. **Do not copy
it.** Single-quote the whole value so the inner double quotes survive
YAML parsing.

`http` is not an error: the binding is authenticated by the thumbprint,
not by TLS. A wrong thumbprint fails at *provision* time, which is the
good kind of failure. A thumbprint copied from the wrong server fails
the same way. Get them from the servers themselves:

```sh
# ===== RUN ON: A NODE =====
curl -s http://tang1.enclave.local:7500/adv | head -c 200; echo
```

> 🚧 **DRAFT -- NOT VALIDATED.** The command that turns that
> advertisement into the thumbprint string has not been run here.
> `clevis` ships a helper for it; confirm the exact invocation and the
> digest algorithm against the Tang version deployed, and record both —
> a thumbprint computed with the wrong digest is a boot failure on every
> node at once.

> ⚠️ **STIG** On TPM v2, reset the TPM chip in firmware before booting
> the ISO. Keys left behind by whatever was on the disk previously can
> stall the deployment, and the symptom is a node that never finishes
> provisioning rather than anything that names the TPM. On a
> re-provisioned enclave host this is the common case, not the edge one.

### What the cipher will be

Unknown, and deliberately not asserted.

On the classic path, `openshift: fips: true` in a Butane config is what
makes the rendered MachineConfig select `aes-cbc-essiv:sha256` instead
of `aes-xts-plain64`. On this path there is no Butane config and no
cipher field — the assisted installer generates the LUKS configuration
itself, and whether it reads the cluster's `fips: true` and picks the
FIPS-permitted cipher has not been established here.

That makes the `cryptsetup luksDump` check at the end of this section
load-bearing rather than confirmatory. Run it on the first node that
comes up, before the rest of the install proceeds, and record what it
says — in either direction. If the cipher is wrong, finding out at that
moment costs a reinstall of one cluster that is not yet carrying
anything.

### What is not settled

- **`/boot` is not encrypted.** It holds the kernel, the initramfs and
  the Clevis binding, and something has to be readable before anything
  can be decrypted. Root is encrypted; `/boot` is not. Say so in the
  evidence pack rather than letting an assessor discover it, and confirm
  the current behaviour for the release you install — this has moved.
- **What `enableOn: all` covers.** It is documented as selecting nodes,
  not filesystems. That the filesystem it encrypts on each node is the
  root volume and nothing else is an assumption here. Confirm it with
  `lsblk --fs` against every mount a node actually has, not just `root`.
- **Tang key rotation bricks nodes.** A Tang server rebuilt with new
  keys no longer satisfies a binding made against the old thumbprint,
  and every node that depended on it fails to boot — not at rotation
  time, at the next reboot, which may be months later and during an
  unrelated change. The rebinding procedure has not been established
  here. Establish it, and write it down somewhere the Tang owner will
  find it, before the servers go into normal patching.

### Tang, if you are using it

Tang is infrastructure, not content — nothing here needs mirroring, no
extra images, no change to prep's ImageSetConfiguration. But a Tang
server that does not exist yet is a blocker discovered at install time,
on the wrong side of the airgap.

📌 **Handoff** Tang servers are a cluster dependency with the same
standing as the mirror registry. If they go away, nodes do not boot. They
need the same backup, patching and change control, and whoever owns them
needs to know that.

### Verify afterwards

From a debug shell, once nodes are up:

```sh
# ===== RUN ON: A NODE =====
lsblk --fs                    # root partition shows crypto_LUKS
cryptsetup status root        # type: LUKS2
```

Capture this output per node. Chapter 12 wants it.

> 🚧 **DRAFT -- NOT VALIDATED.** Written from documentation, not executed
> against a cluster. Verify before running. Replace this block with the
> command as run, then update VALIDATION.md.
>
> `cryptsetup status` proves the volume is LUKS2. It does not prove
> *what unlocks it*, which is the part a wrong `diskEncryption` block
> could have got wrong, and the part the accreditation is actually
> about. The binding is what to look at:

```sh
# ===== RUN ON: A NODE =====
sudo clevis luks list -d /dev/disk/by-partlabel/root
sudo cryptsetup luksDump /dev/disk/by-partlabel/root | grep -i cipher
```

Read the `clevis luks list` output against what you asked for. A `tpm2`
pin on a cluster configured `mode: tang` means the block did not take
and the node is unlocking on the TPM alone — booting normally, passing
every health check, and not meeting the control. **No pin at all means
`enableOn` never reached the installer**, which is the default-to-`none`
failure, and it is the one to look for first.

The cipher line is the open question, not a confirmation. See *What the
cipher will be* above: `aes-cbc-essiv:sha256` is what a `fips: true`
cluster should carry, `aes-xts-plain64` is the non-FIPS default, and
which one this path actually produces is unestablished. Record whichever
you get.

## Default-deny NetworkPolicy project template

The requirement: a newly created project denies all ingress by default,
so that a workload is reachable only where someone has written a policy
saying so.

The failure mode it prevents: OpenShift's default is that every pod in
every namespace can reach every other pod. In a hardened build that is a
finding on its own, but the operational version of the problem is worse —
it means the security posture of the cluster degrades every time anybody
creates a project, silently, with no event and nothing to review.

This is done by replacing the **project template**, so that the
`NetworkPolicy` objects are created as part of project creation rather
than bolted on afterwards. Doing it at the manifest stage rather than on
day 1 means there is never a window in which a project was created
without them.

> 🚧 **DRAFT -- NOT VALIDATED.** Written from documentation, not executed
> against a cluster. Verify before running. Replace this block with the
> command as run, then update VALIDATION.md.
>
> Two separate uncertainties here, and the second is the one that
> decides where this section lives. First: whether the installer will
> accept a `Template` and a `Project` config CR dropped into
> `openshift/` at all — the `Project` resource named `cluster` is one the
> installer generates itself, so supplying a second may conflict rather
> than merge. Second: the **namespace selector labels differ between the
> ingress policy and the monitoring policy**, for historical reasons,
> and getting one of them wrong produces exactly the symptom the
> paragraph above warns about. Verify both label strings against the
> release you install before trusting this.
>
> If the install-time route turns out not to work, this moves to
> [06-day1-cluster-config.md](06-day1-cluster-config.md) as a day-1
> patch. **Say so here when you find out**, and tick the "explicitly
> deferred" line in the checklist below rather than leaving it
> ambiguous.

Start from the default template rather than writing one, because it
carries the project-creation machinery you do not want to reinvent:

```sh
# ===== RUN ON: THE INSTALL HOST =====
: "${OCP_INSTALL_ROOT:?set it first -- see 01-intake.md}"
oc adm create-bootstrap-project-template -o yaml \
  > ${OCP_INSTALL_ROOT}/manifests-src/project-template.yaml
```

Then add the policies to its `objects:` list. Four of them, and each
one exists because of a specific thing that breaks without it:

```yaml
# ===== EDIT IN: ${OCP_INSTALL_ROOT}/manifests-src/project-template.yaml =====
objects:
# ... the existing Project / RoleBinding objects stay as generated ...
- apiVersion: networking.k8s.io/v1
  kind: NetworkPolicy
  metadata:
    name: deny-by-default
    namespace: ${PROJECT_NAME}
  spec:
    podSelector: {}
    policyTypes:
    - Ingress
- apiVersion: networking.k8s.io/v1
  kind: NetworkPolicy
  metadata:
    name: allow-from-same-namespace
    namespace: ${PROJECT_NAME}
  spec:
    podSelector: {}
    ingress:
    - from:
      - podSelector: {}
- apiVersion: networking.k8s.io/v1
  kind: NetworkPolicy
  metadata:
    name: allow-from-openshift-ingress
    namespace: ${PROJECT_NAME}
  spec:
    podSelector: {}
    policyTypes:
    - Ingress
    ingress:
    - from:
      - namespaceSelector:
          matchLabels:
            policy-group.network.openshift.io/ingress: ""
- apiVersion: networking.k8s.io/v1
  kind: NetworkPolicy
  metadata:
    name: allow-from-openshift-monitoring
    namespace: ${PROJECT_NAME}
  spec:
    podSelector: {}
    policyTypes:
    - Ingress
    ingress:
    - from:
      - namespaceSelector:
          matchLabels:
            network.openshift.io/policy-group: monitoring
```

- **`deny-by-default`** is a policy with an empty `podSelector` and no
  `ingress` rules. That is what "deny" is spelled as — there is no
  `deny` keyword. Its presence is what flips the namespace from
  allow-all to deny-all; everything below it is an exception to it.
- **`allow-from-same-namespace`** keeps a multi-pod application working.
  Without it a web pod cannot reach its own database and the
  application looks broken on deploy.
- **`allow-from-openshift-ingress`** is the one whose absence is
  misdiagnosed. Routes stay `Admitted`, the ingress controller stays
  healthy, and every request returns `503`. It reads as an ingress
  problem for as long as you let it.
- **`allow-from-openshift-monitoring`** is the one whose absence is
  never diagnosed at all. Prometheus simply does not scrape, the
  `ServiceMonitor` reports no error, and the dashboards are empty — a
  compliance problem as much as an operational one, since chapter 12
  wants monitoring coverage.

**Note the two different label keys.** Ingress uses
`policy-group.network.openshift.io/ingress` with an empty-string value;
monitoring uses `network.openshift.io/policy-group: monitoring`. The
key order is reversed between them. That is not a typo in this
document, and the two are not interchangeable. Both labels are applied
to those namespaces by the platform — never set them yourself.

Point the cluster at the template:

```yaml
# ===== EDIT IN: ${OCP_INSTALL_ROOT}/manifests-src/project-config.yaml =====
apiVersion: config.openshift.io/v1
kind: Project
metadata:
  name: cluster
spec:
  projectRequestTemplate:
    name: project-request
```

The `Template` must land in the `openshift-config` namespace and the
`Project` CR is cluster-scoped and named `cluster`. Verify after the
cluster is up, with a throwaway project — this is the only check that
means anything:

```sh
# ===== RUN ON: THE CLUSTER =====
oc new-project policy-smoke-test
oc get networkpolicy -n policy-smoke-test
oc delete project policy-smoke-test
```

Four policies listed is the pass. Zero means the template is not wired
up, and every project created in the meantime is a project you now have
to audit.

> ⚠️ **STIG** Whichever way it lands, the control is about *new* projects.
> Projects created before the template is in place keep the old
> behaviour. If this ends up as a day-1 step, chapter 12 must record which
> namespaces predate it — `openshift-*` namespaces always will.

## Chrony

The requirement: every node synchronises time against the enclave's NTP
source, from first boot, without ever attempting to reach a public pool.

The failure mode it prevents is the one chapter 1 flagged: certificate
validation fails on skew, and the symptom is TLS errors that say nothing
about time. At install time it is worse than that, because a node whose
clock is wrong may fail to join at all, and the bootstrap log will tell
you about certificates.

Why it belongs in this window rather than on day 1: the nodes need
working time *during* bootstrap, which is before there is a cluster to
apply a MachineConfig to.

> 🚧 **DRAFT -- NOT VALIDATED.** Written from documentation, not executed
> against a cluster. Verify before running. Replace this block with the
> command as run, then update VALIDATION.md.
>
> The shape is documented and low-risk compared to disk encryption, but
> **the encoding is the part that fails quietly.** A base64 blob that is
> truncated, line-wrapped, or built from the wrong file produces a
> MachineConfig that applies cleanly and leaves a node pointing at a
> pool it cannot reach. Nothing reports it. Use Butane's `inline:` form
> rather than encoding by hand, and if you must encode by hand, read the
> warning below.
>
> There is also a second, partly-overlapping route: `additionalNTPSources`
> in `agent-config.yaml` ([02](02-install-config.md)). It covers
> discovery and bootstrap. Whether it also persists into the installed
> node's `chrony.conf` has not been established here — assume it does
> not, and set both.

```yaml
# ===== EDIT IN: ${OCP_INSTALL_ROOT}/manifests-src/98-master-chrony.bu =====
variant: openshift
version: 4.21.0
metadata:
  name: 98-master-chrony
  labels:
    machineconfiguration.openshift.io/role: master
storage:
  files:
  - path: /etc/chrony.conf
    mode: 0644
    overwrite: true
    contents:
      inline: |
        server 10.20.30.2 iburst
        server 10.20.30.3 iburst
        driftfile /var/lib/chrony/drift
        makestep 1.0 3
        rtcsync
        logdir /var/log/chrony
```

The `worker` twin is the same file with `worker` in both the name and
the role label. **Both are required even on a cluster with no workers
today.** A pool with no machines costs nothing; a worker added in six
months to a cluster that only ever had a `master` chrony config comes up
pointing at a public pool it cannot reach, and nobody is watching for it
then.

Three details carry the whole thing:

- **`overwrite: true`.** Without it, Ignition refuses to replace the
  `/etc/chrony.conf` that RHCOS already ships, and the node keeps the
  default — which points at a public pool. This is the quiet failure.
- **`server`, not `pool`.** The RHCOS default uses `pool`, which
  expects a name that resolves to several addresses. In an enclave you
  have specific hosts. A `pool` directive against a single-address name
  works but obscures what is configured, and the evidence pack has to
  state the time source.
- **No public pool line survives.** The file is replaced wholesale, not
  merged. That is the intent: there must be no fallback to
  `*.pool.ntp.org`, because a node that reaches a public NTP server is
  a node that reached the internet.

`butane` is **not in the handoff bundle.** Prep ships
`openshift-install-fips` and `oc` and nothing else. Getting it is a prep
Day-2 delta and a transfer window — see [13-day2.md](13-day2.md). The
by-hand encoding below is the fallback, and it is a fallback, not an
equivalent: the `data:` URL is where hand-built MachineConfigs go wrong.

> ⚠️ **STIG** `butane`, once it arrives, is a new binary on a hardened
> host and will not execute until it is relabelled and trusted, in that
> order: `restorecon` then `fapolicyd-cli --file add`. Per host.
> Chapter 1 does the same dance for the installer.

Compile and stage:

```sh
# ===== RUN ON: THE INSTALL HOST =====
: "${OCP_INSTALL_ROOT:?set it first -- see 01-intake.md}"
cd ${OCP_INSTALL_ROOT}/manifests-src
butane 98-master-chrony.bu -o 98-master-chrony.yaml
butane 98-worker-chrony.bu -o 98-worker-chrony.yaml
```

The rendered file carries the config as a `data:` URL under
`spec.config.storage.files[].contents.source`. If you are building that
by hand because `butane` is not available, the encoding must be
unwrapped — `base64 -w0`, with no newline inserted anywhere — and the
prefix is `data:text/plain;charset=utf-8;base64,`. A wrapped blob is
still valid YAML, still applies, and decodes to a truncated file.
Check by decoding your own output back before you trust it:

```sh
# ===== RUN ON: THE INSTALL HOST =====
: "${OCP_INSTALL_ROOT:?set it first -- see 01-intake.md}"
grep -o 'base64,[A-Za-z0-9+/=]*' \
  ${OCP_INSTALL_ROOT}/manifests-src/98-master-chrony.yaml |
  cut -d, -f2 | base64 -d
```

What comes back must be your `chrony.conf`, complete, last line
included.

Verify afterwards:

```sh
# ===== RUN ON: A NODE =====
chronyc sources
chronyc tracking
```

`chronyc sources` must list your enclave source and nothing else. A `^?`
against a public pool address means the default configuration survived.
