# Day-2

Keeping a hardened, airgapped cluster patched, scanned and evidenced
after the build is over.

The structural fact that shapes all of it: **this cluster cannot fetch
anything.** Every patch, every operator update, every new image is a
prep cycle and a transfer window, measured in days. That changes how
patching is planned, not just how it is executed.

---

## Patching hands back to prep

Nothing in this repository mirrors content. When the cluster needs a
z-stream, a new operator, or an updated Compliance Operator, the work
happens on the other side of the airgap:

> [disconnected-prep — Day-2 delta updates](https://github.com/bgregori/disconnected-prep/blob/main/docs/09-day2-delta.md)

Prep's loop in one line: re-run the mirror against the **same**
destination so the incremental history applies, package, transfer, push.
Measured there at 9.1 GB for one added operator against a 29 GB initial
mirror.

Two things from that chapter that the install side needs to know,
because they are the ones that produce surprises here:

- **The delta is cheap only if prep kept its history.**
  `mirror-out/working-dir/.history/` on the connected bastion is what
  makes a 9 GB transfer instead of a 29 GB one. If it was deleted —
  bastion rebuilt, directory tidied — your next patch is a full
  re-mirror and a much longer window. Worth confirming it still exists
  *before* you plan a patch cycle, not after.
- **Only what was mirrored exists.** An operator absent from prep's
  `imageset-config.yaml` is not installable, and finding that out is a
  transfer window. This is why [chapter 1](01-intake.md#the-mirror-gate)
  gates on content before the cluster is built.

### What the install side does afterwards

Once prep has pushed new content:

```sh
# ===== RUN ON: THE CLUSTER =====
oc get clusterversion
oc adm upgrade
```

`oc adm upgrade` lists what is available **locally** when the update
service is running against the mirrored graph — see
[chapter 6](06-day1-cluster-config.md#the-update-service). Without OSUS,
upgrades are by digest.

## Re-scan cadence

A scan result is a statement about a moment. The pack from
[chapter 12](12-evidence-pack.md) decays from the day it is signed.

| Trigger | Scan | Why |
|---|---|---|
| Cluster upgrade | both profiles | platform behaviour changed |
| Compliance Operator update | both profiles | the benchmark content changed; results can move with no cluster change at all |
| MachineConfig change | `rhcos4-stig` | the node configuration changed, which is what that profile measures |
| New operator installed | `ocp4-stig` | new cluster resources, new RBAC, new workloads |
| Periodic | both profiles | agreed with the ISSO — see below |
| Before an assessment | both profiles | obviously |

The periodic interval is an organisational decision, not a technical
one. Ask the ISSO for it rather than choosing one; chapter 12's handover
conversation is where that question belongs.

### Keeping the delta going

The baseline/after pair from chapters 9 and 10 is not a one-off format.
Every subsequent scan is an "after" against the previous one, and the
same two commands produce it:

```sh
# ===== RUN ON: THE CLUSTER =====
: "${OCP_INSTALL_ROOT:?set it first -- see 01-intake.md}"
PREV=${OCP_INSTALL_ROOT}/evidence/<previous-date>
THIS=${OCP_INSTALL_ROOT}/evidence/$(date +%Y-%m-%d)
mkdir -p ${THIS}

oc get compliancecheckresult -A \
  --no-headers -o custom-columns=NAME:.metadata.name,STATUS:.status,SEVERITY:.severity \
  | sort > ${THIS}/summary.txt

diff ${PREV}/summary.txt ${THIS}/summary.txt > ${THIS}/delta.txt
```

`PASS` → `FAIL` between two scans with no intervening change is the
signal worth building a habit around. It means either something drifted
or the content version moved, and both need knowing about.

## File Integrity Operator and drift

The Compliance Operator answers "is the configuration correct". The File
Integrity Operator answers a different question: **has anything on the
nodes changed since it was correct.**

The failure mode it addresses is the one periodic scanning misses
entirely — a file modified on a node between scans, deliberately or
otherwise, and restored before the next one. Or, more commonly and more
usefully: a node that has drifted from its pool's configuration because
somebody fixed something by hand during an incident and never came back
to it.

It is in prep's standard compliance profile alongside the Compliance
Operator, so in a build that followed prep's defaults the content is
already in the mirror. Confirm:

```sh
# ===== RUN ON: THE CLUSTER =====
oc get packagemanifest -A | grep -i file-integrity
```

## What else drifts

Things that are correct at handover and silently stop being correct.
Each needs an owner and a date, not just a mention.

| | Breaks when | Symptom |
|---|---|---|
| **IdP CA** | it expires | nobody can log in, with no warning |
| **IdP client secret** | it is rotated without telling you | nobody can log in |
| **Registry CA** | it expires | nodes cannot pull; running workloads fine until they are not |
| **Tang servers** | rebuilt with new keys | **nodes do not boot** |
| **NTP source** | decommissioned | certificate errors that do not mention time |
| **Audit destination** | reconfigured by the SIEM team | records stop arriving; nothing in the cluster notices |
| **Mirror registry** | runs out of disk | pulls fail; see prep's capacity planning |
| **Group membership** | people leave | cluster-admin held by someone who left |

The Tang row is the one to put in front of whoever owns those servers.
Every other row degrades something; that one prevents nodes from
booting, and it will be discovered during an unrelated maintenance
reboot at the worst possible time.

The registry disk row is prep's
[capacity planning chapter](https://github.com/bgregori/disconnected-prep/blob/main/docs/10-capacity-planning.md):
each retained OpenShift version costs close to a full payload, roughly
19 GiB, and nothing is reclaimed automatically.

## The recurring calendar

Everything above, as the thing to actually put in a calendar:

- **Per patch cycle** — prep delta, upgrade, re-scan both profiles,
  update the evidence pack delta, reinitialise File Integrity
- **Per agreed interval** — re-scan, RBAC review
  ([chapter 11](11-manual-controls.md#rbac-review)), exceptions register
  review dates
- **Annually, or on the ISSO's cycle** — full evidence pack refresh
- **On a date you set now** — IdP CA expiry, registry CA expiry, client
  secret rotation

The last line is the one that is never done, because it is the only one
with no natural trigger. Put the expiry dates in a calendar on the day
you read them, in [chapter 7](07-identity.md#step-2--the-idp-ca).
