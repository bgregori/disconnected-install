# Day-2

Keeping a hardened, airgapped cluster patched, scanned and evidenced
after the build is over.

The structural fact that shapes all of it: **this cluster cannot fetch
anything.** Every patch, every operator update, every new image is a
prep cycle and a transfer window, measured in days. That changes how
patching is planned, not just how it is executed.

---

## Patching hands back to prep

Nothing in this repository mirrors content. When the cluster needs a
z-stream, a new operator, or an updated Compliance Operator, the work
happens on the other side of the airgap:

> [disconnected-prep — Day-2 delta updates](https://github.com/bgregori/disconnected-prep/blob/main/docs/09-day2-delta.md)

Prep's loop in one line: re-run the mirror against the **same**
destination so the incremental history applies, package, transfer, push.
Measured there at 9.1 GB for one added operator against a 29 GB initial
mirror.

Two things from that chapter that the install side needs to know,
because they are the ones that produce surprises here:

- **The delta is cheap only if prep kept its history.**
  `mirror-out/working-dir/.history/` on the connected bastion is what
  makes a 9 GB transfer instead of a 29 GB one. If it was deleted —
  bastion rebuilt, directory tidied — your next patch is a full
  re-mirror and a much longer window. Worth confirming it still exists
  *before* you plan a patch cycle, not after.
- **Only what was mirrored exists.** An operator absent from prep's
  `imageset-config.yaml` is not installable, and finding that out is a
  transfer window. This is why [chapter 1](01-intake.md#the-mirror-gate)
  gates on content before the cluster is built.

### What the install side does afterwards

Once prep has pushed new content:

```sh
# ===== RUN ON: THE CLUSTER =====
oc get clusterversion
oc adm upgrade
```

`oc adm upgrade` lists what is available **locally** when the update
service is running against the mirrored graph — see
[chapter 6](06-day1-cluster-config.md#the-update-service). Without OSUS,
upgrades are by digest.

Everything in the rest of this section is drafted. Prep's validation
record notes that the OSUS path has not been executed on either side of
the airgap, and nothing below has been seen working here; the failure
modes named are the ones the documentation implies, not ones anybody
has watched. Each block carries its own marker, because the one you
read may be the only one you read.

### Before either upgrade form

Four preconditions, and the first is the one that fails:

1. **The release signature is in the cluster.** The Cluster Version
   Operator verifies the release image against a signature before it
   will apply it, and in a disconnected cluster that signature arrives
   as a `ConfigMap` applied from prep's handoff — the same
   `cluster-resources/` directory
   [chapter 6](06-day1-cluster-config.md#apply-the-cluster-resources)
   applies. Prep's record is explicit that the signature artifacts are
   **files**, not a `signatures/` directory, which is exactly how one
   gets missed on the second pass.
2. **The new payload is actually in the registry** — prep pushed it, not
   just mirrored it locally.
3. **Every MachineConfigPool is settled** before you start. An upgrade
   on top of an in-flight rollout is a long, confusing afternoon.
4. **MachineHealthChecks paused**, if any exist. A node that takes too
   long to come back during an upgrade is normal; a health check that
   deletes it is not.

> 🚧 **DRAFT -- NOT VALIDATED.** Written from documentation, not executed
> against a cluster. Verify before running. Replace this block with the
> command as run, then update VALIDATION.md.

```sh
# ===== RUN ON: THE CLUSTER =====
: "${OCP_INSTALL_ROOT:?set it first -- see 01-intake.md}"
oc apply -f ${OCP_INSTALL_ROOT}/handoff/cluster-resources/
oc get configmap -n openshift-config-managed | grep -i signature
oc get machineconfigpool
oc get machinehealthcheck -A
```

The last line finds them; pausing is a separate per-resource action,
and on a bare-metal cluster there are often none at all. "None exist"
is a valid answer to precondition 4 — write it down rather than
leaving the box ambiguous.

### Upgrading with OSUS

> 🚧 **DRAFT -- NOT VALIDATED.** Written from documentation, not executed
> against a cluster. Verify before running. Replace this block with the
> command as run, then update VALIDATION.md.

```sh
# ===== RUN ON: THE CLUSTER =====
oc get clusterversion version -o jsonpath='{.spec.upstream}{"\n"}'
oc adm upgrade
oc adm upgrade --to <version>
```

`.spec.upstream` must point at the local update service route, not at
`api.openshift.com`. If it points outward, `oc adm upgrade` reports no
updates — which reads as "there is nothing to install" and means "this
cluster cannot see a graph". That sentence is the single most likely
way to waste a change window here.

### Upgrading by digest, without OSUS

> 🚧 **DRAFT -- NOT VALIDATED.** Written from documentation, not executed
> against a cluster. Verify before running. Replace this block with the
> command as run, then update VALIDATION.md.

```sh
# ===== RUN ON: THE CLUSTER =====
oc adm release info <registry>:<port>/<repo>:<version>-<arch> \
  -o jsonpath='{.digest}{"\n"}'

oc adm upgrade --allow-explicit-upgrade \
  --to-image <registry>:<port>/<repo>@sha256:<digest>
```

> ⚠️ **STIG** `--allow-explicit-upgrade` bypasses the graph, and the
> graph is what normally refuses an unsupported jump. Nothing will stop
> you skipping a minor version or moving to a payload that was never
> intended for this path. You are the edge validation. Write the
> source and target versions in the change request, and check them
> against Red Hat's supported upgrade paths **before** the airgap, while
> you still have a browser.

### Watching the upgrade

```sh
# ===== RUN ON: THE CLUSTER =====
oc get clusterversion
oc get clusteroperators
oc get machineconfigpool
oc get nodes
```

The two failures worth recognising on sight:

- **A refusal that mentions verification or keyrings**, not the
  network. That is the missing signature `ConfigMap` from precondition
  1, and no amount of retrying fixes it.
- **`oc adm upgrade` listing nothing with OSUS in place.** Three
  candidates, in order of likelihood: prep mirrored without the graph,
  the update service operator was never in prep's operator list, or
  `.spec.upstream` still points at Red Hat.

A payload upgrade reboots every node in sequence, with all that implies
for [single node](topologies/sno.md) and
[three-node compact](topologies/compact.md). Read the topology page
before scheduling the window, not during it.

> **A cluster upgrade is also a compliance event.** New platform
> behaviour can change scan results without anybody touching
> configuration. Re-scan after every upgrade — see the cadence table
> below — and keep the result, because "the scan changed and we do not
> know when" is a bad position.

## Re-scan cadence

A scan result is a statement about a moment. The pack from
[chapter 12](12-evidence-pack.md) decays from the day it is signed.

| Trigger | Scan | Why |
|---|---|---|
| Cluster upgrade | both profiles | platform behaviour changed |
| Compliance Operator update | both profiles | the benchmark content changed; results can move with no cluster change at all |
| MachineConfig change | `rhcos4-stig` | the node configuration changed, which is what that profile measures |
| New operator installed | `ocp4-stig` | new cluster resources, new RBAC, new workloads |
| Periodic | both profiles | agreed with the ISSO — see below |
| Before an assessment | both profiles | obviously |

The periodic interval is an organisational decision, not a technical
one. Ask the ISSO for it rather than choosing one; chapter 12's handover
conversation is where that question belongs.

### Scheduling the periodic scan

The resources below are drafted; each carries its own marker. The
read-only `oc get` queries are not.

Recurring scans are a property of the `ScanSetting` the binding points
at, not a separate mechanism. Look at what the operator shipped before
writing anything:

```sh
# ===== RUN ON: THE CLUSTER =====
oc get scansetting -n <compliance-namespace>
oc get scansetting -n <compliance-namespace> -o yaml
```

Two are created by default. Their names are a trap worth reading
slowly:

| `ScanSetting` | What it does |
|---|---|
| `default` | scheduled scan, remediations **not** applied automatically |
| `default-auto-apply` | the same schedule, with `autoApplyRemediations` and `autoUpdateRemediations` set to `true` |

> ⚠️ **STIG** Do not bind a profile to `default-auto-apply` on this
> cluster. It applies remediations the moment a scan finds them, which
> means MachineConfig rollouts — node reboots — triggered by a cron
> entry, with nobody watching and no review.
> [Chapter 10's whole argument](10-remediation.md#why-review-then-apply-is-the-default)
> is that remediations are read before they are applied; a scheduled
> auto-apply undoes that decision silently, months after anyone
> remembers making it.

The fields that matter on a `ScanSetting`, and what they do to your
evidence:

| Field | Effect |
|---|---|
| `schedule` | cron. The shipped default is daily at 01:00. |
| `rawResultStorage.rotation` | how many raw result sets are kept in the volume before the oldest is discarded. Default is 3. `0` disables rotation. |
| `rawResultStorage.size` | the PV size. Default 1Gi. |
| `rawResultStorage.storageClassName` | required if the cluster has no default storage class — which is common in an enclave |

The second row is the one that decides what your evidence is worth, and
it cuts both ways:

- **The raw results rotate.** Three scans after the baseline, the
  baseline's raw report is gone from the cluster.
- **The `ComplianceCheckResult` objects do not accumulate at all.** Each
  scan reconciles them in place, so the API only ever shows the latest
  verdict. There is no "previous scan" to go back to.

So a schedule does not *overwrite* your baseline so much as render the
cluster incapable of remembering it. Which is fine, and is why chapter 9
copies results off the moment they are taken:

> **The baseline lives off the cluster, permanently.** Nothing you
> configure here changes that, and nothing you configure here should be
> relied on to preserve it. On-cluster results are transient by design.
> See also
> [chapter 12 on raw results](12-evidence-pack.md#two-kinds-of-result-and-only-one-of-them-is-durable).

A scan setting for a cluster that is keeping evidence, then: the agreed
interval, rotation raised enough that a missed collection is not a lost
scan, and remediation left manual.

> 🚧 **DRAFT -- NOT VALIDATED.** Written from documentation, not executed
> against a cluster. Verify before running. Replace this block with the
> command as run, then update VALIDATION.md.

```yaml
# ===== EDIT IN: ${OCP_INSTALL_ROOT}/day2/scansetting-stig.yaml =====
apiVersion: compliance.openshift.io/v1alpha1
kind: ScanSetting
metadata:
  name: stig-periodic
  namespace: <compliance-namespace>
schedule: '0 2 * * 0'          # the interval the ISSO agreed, not this one
rawResultStorage:
  rotation: 10                 # 0 disables rotation entirely
  size: 5Gi
  storageClassName: <storage-class>
roles:
  - master
  - worker
scanTolerations:
  - effect: NoSchedule
    key: node-role.kubernetes.io/master
    operator: Exists
```

Then bind the profiles to it exactly as chapter 9 bound them to the
one-shot setting, and confirm the schedule took:

> 🚧 **DRAFT -- NOT VALIDATED.** Written from documentation, not executed
> against a cluster. Verify before running. Replace this block with the
> command as run, then update VALIDATION.md.

```sh
# ===== RUN ON: THE CLUSTER =====
: "${OCP_INSTALL_ROOT:?set it first -- see 01-intake.md}"
oc apply -f ${OCP_INSTALL_ROOT}/day2/scansetting-stig.yaml
oc get scansettingbinding -n <compliance-namespace>
oc get pvc -n <compliance-namespace>
```

The `pvc` line is not an afterthought. A scan whose result volume
cannot bind does not fail loudly — it sits in a pending phase looking
like a long-running scan, and the first anyone notices is a month of
missing results during the assessment.

Three things to establish on the first real scheduled run, because they
are what this draft cannot tell you:

1. Whether the scheduled scan reuses the same `ComplianceScan` objects
   or creates new ones — which decides whether the capture commands
   below need adjusting.
2. How long a full two-profile scan takes on this cluster, so the
   schedule does not overlap itself.
3. Whether the PV sizing survives the rotation count you chose.

### Keeping the delta going

The baseline/after pair from chapters 9 and 10 is not a one-off format.
Every subsequent scan is an "after" against the previous one, and the
same two commands produce it:

```sh
# ===== RUN ON: THE CLUSTER =====
: "${OCP_INSTALL_ROOT:?set it first -- see 01-intake.md}"
PREV=${OCP_INSTALL_ROOT}/evidence/<previous-date>
THIS=${OCP_INSTALL_ROOT}/evidence/$(date +%Y-%m-%d)
mkdir -p ${THIS}

oc get compliancecheckresult -A \
  --no-headers -o custom-columns=NAME:.metadata.name,STATUS:.status,SEVERITY:.severity \
  | sort > ${THIS}/summary.txt

diff ${PREV}/summary.txt ${THIS}/summary.txt > ${THIS}/delta.txt
```

`PASS` → `FAIL` between two scans with no intervening change is the
signal worth building a habit around. It means either something drifted
or the content version moved, and both need knowing about.

## File Integrity Operator and drift

The Compliance Operator answers "is the configuration correct". The File
Integrity Operator answers a different question: **has anything on the
nodes changed since it was correct.**

The failure mode it addresses is the one periodic scanning misses
entirely — a file modified on a node between scans, deliberately or
otherwise, and restored before the next one. Or, more commonly and more
usefully: a node that has drifted from its pool's configuration because
somebody fixed something by hand during an incident and never came back
to it.

It is in prep's standard compliance profile alongside the Compliance
Operator, so in a build that followed prep's defaults the content is
already in the mirror. Confirm:

```sh
# ===== RUN ON: THE CLUSTER =====
oc get packagemanifest -A | grep -i file-integrity
```

Nothing listed is the same answer as everywhere else in this
repository: a prep delta and a transfer window.
[Chapter 1's mirror gate](01-intake.md#the-mirror-gate) names
`file-integrity-operator` specifically so that this is discovered
before the cluster exists rather than six months after.

### Installing it

The operator installs into its own namespace, and as in
[chapter 9](09-compliance-operator.md#installing) the part a generic
walkthrough gets wrong on a disconnected cluster is the
`Subscription` — `source` must name **prep's** `CatalogSource`, the one
[chapter 6](06-day1-cluster-config.md#disable-the-default-catalog-sources)
left behind after `disableAllDefaultSources`, not the default one that
no longer exists.

> 🚧 **DRAFT -- NOT VALIDATED.** Written from documentation, not executed
> against a cluster. Verify before running. Replace this block with the
> command as run, then update VALIDATION.md.

```yaml
# ===== EDIT IN: ${OCP_INSTALL_ROOT}/day2/file-integrity-operator.yaml =====
apiVersion: v1
kind: Namespace
metadata:
  name: openshift-file-integrity
---
apiVersion: operators.coreos.com/v1
kind: OperatorGroup
metadata:
  name: file-integrity-operator
  namespace: openshift-file-integrity
spec:
  targetNamespaces:
    - openshift-file-integrity
---
apiVersion: operators.coreos.com/v1alpha1
kind: Subscription
metadata:
  name: file-integrity-operator
  namespace: openshift-file-integrity
spec:
  channel: <channel>
  name: file-integrity-operator
  source: <prep's CatalogSource name>
  sourceNamespace: openshift-marketplace
```

> 🚧 **DRAFT -- NOT VALIDATED.** Written from documentation, not executed
> against a cluster. Verify before running. Replace this block with the


Get the channel and the catalog name from the packagemanifest above
rather than from this page — both are properties of what prep mirrored,
and neither is guessable.

Then one `FileIntegrity` resource per node role, because a control
plane node and a worker have legitimately different files:

> 🚧 **DRAFT -- NOT VALIDATED.** Written from documentation, not executed
> against a cluster. Verify before running. Replace this block with the
> command as run, then update VALIDATION.md.

```yaml
# ===== EDIT IN: ${OCP_INSTALL_ROOT}/day2/fileintegrity-master.yaml =====
apiVersion: fileintegrity.openshift.io/v1alpha1
kind: FileIntegrity
metadata:
  name: master-fileintegrity
  namespace: openshift-file-integrity
spec:
  nodeSelector:
    node-role.kubernetes.io/master: ""
  tolerations:
    - effect: NoSchedule
      key: node-role.kubernetes.io/master
      operator: Exists
```

On [single node](topologies/sno.md) there is one pool and one resource,
not two.

```sh
# ===== RUN ON: THE CLUSTER =====
oc get fileintegrity -n openshift-file-integrity
oc get fileintegritynodestatus -n openshift-file-integrity
```

`FileIntegrityNodeStatus` — one object per node — is the artifact. A
node reads `Succeeded` or `Failed`, and a `Failed` node carries the list
of files that changed. That per-node list is what the evidence pack
wants, and it is also the thing that is useless without the next
section.

### Re-baselining, which is the whole point

The operator has to be told that a new state is the expected state.
Doing that is one annotation:

> 🚧 **DRAFT -- NOT VALIDATED.** Written from documentation, not executed
> against a cluster. Verify before running. Replace this block with the
> command as run, then update VALIDATION.md.

```sh
# ===== RUN ON: THE CLUSTER =====
oc annotate fileintegrity/master-fileintegrity \
  -n openshift-file-integrity file-integrity.openshift.io/re-init=
```

Two facts worth knowing before you need them, both from the
documentation and neither confirmed here:

- **Routine MachineConfig rollouts are supposed to handle themselves.**
  The operator watches node objects and suspends scanning while a node
  is updating through the MachineConfig API, re-initialising when the
  update completes. So a normal patch cycle should *not* produce a
  storm of drift. It is natural to assume the opposite — that every
  rollout lights up every node — and the distinction matters: the pause
  applies only to changes that go through the MCO and are visible in
  node annotations. Anything changed on a node by hand, or by anything
  outside the MCO, is a genuine finding, which is the behaviour you
  wanted.
- **Re-initialising does not clear the record.** The old database and
  logs are backed up on the node, and prior failures remain visible in
  `FileIntegrityNodeStatus`. The config maps the operator generates are
  not garbage-collected with the resource, so cleanup is manual. For
  evidence this is an advantage: the history survives the re-baseline.
  For operations it means "we re-initialised" is not the same as "the
  alert went away".

So the procedure to establish on first use is narrower than it looks —
not "re-baseline after every change", but **"confirm the automatic
re-initialisation happened, and re-initialise by hand only when it did
not, or when a change arrived from outside the MCO."** Verify that
automatic behaviour on this cluster before relying on it. Either way:

> **An integrity monitor that cries wolf after every patch cycle gets
> ignored within two months.** Establish what a normal patch cycle does
> to `FileIntegrityNodeStatus` before you give the alerts to anyone, not
> after.

Each node that stays `Failed` needs a disposition, in writing, the same
way a `FAIL` does in
[chapter 12's exceptions register](12-evidence-pack.md#the-exceptions-register).
"Known drift on node 3, nobody remembers why" is the state this operator
exists to prevent, and it is also the state it most easily produces.

📌 **Handoff** Drift alerts need a recipient and a response procedure.
An alert nobody owns is not a control. Agree who sees them and what they
do, and record it in the evidence pack.

## What else drifts

Things that are correct at handover and silently stop being correct.
Each needs an owner and a date, not just a mention.

| | Breaks when | Symptom |
|---|---|---|
| **IdP CA** | it expires | nobody can log in, with no warning |
| **IdP client secret** | it is rotated without telling you | nobody can log in |
| **Registry CA** | it expires | nodes cannot pull; running workloads fine until they are not |
| **Tang servers** | rebuilt with new keys | **nodes do not boot** |
| **NTP source** | decommissioned | certificate errors that do not mention time |
| **Audit destination** | reconfigured by the SIEM team | records stop arriving; nothing in the cluster notices |
| **Mirror registry** | runs out of disk | pulls fail; see prep's capacity planning |
| **Group membership** | people leave | cluster-admin held by someone who left |

The Tang row is the one to put in front of whoever owns those servers.
Every other row degrades something; that one prevents nodes from
booting, and it will be discovered during an unrelated maintenance
reboot at the worst possible time.

The registry disk row is prep's
[capacity planning chapter](https://github.com/bgregori/disconnected-prep/blob/main/docs/10-capacity-planning.md):
each retained OpenShift version costs close to a full payload, roughly
19 GiB, and nothing is reclaimed automatically.

## The recurring calendar

Everything above, as the thing to actually put in a calendar:

- **Per patch cycle** — confirm prep still has its mirror history, prep
  delta, apply the new signature `ConfigMap`, upgrade, re-scan both
  profiles, update the evidence pack delta, confirm every node
  re-baselined in File Integrity
- **Per agreed interval** — re-scan, RBAC review
  ([chapter 11](11-manual-controls.md#rbac-review)), exceptions register
  review dates
- **Annually, or on the ISSO's cycle** — full evidence pack refresh
- **On a date you set now** — IdP CA expiry, registry CA expiry, client
  secret rotation

The last line is the one that is never done, because it is the only one
with no natural trigger. Put the expiry dates in a calendar on the day
you read them, in [chapter 7](07-identity.md#step-2--the-idp-ca).

Every drafted block in this chapter is a line in that calendar too,
until it is replaced. A patch cycle run from a draft produces a cluster
that is patched and an evidence pack that cannot say how — see
[chapter 12](12-evidence-pack.md#a-draft-is-never-evidence).
